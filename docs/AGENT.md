# Агент, MCP и расширение

## Ответственности

| Файл или группа | Задача |
|---|---|
| `Hosting/BotComposition.cs` | Создаёт репозитории, сценарии и Telegram-обработчик |
| `Domain/DialogueService.cs` | Читает настройки и историю, последовательно обрабатывает чат, сохраняет успешную пару |
| `Agent/AgentEngine.cs` | Управляет раундами, лимитом действий, уточнениями и аудитом |
| `Agent/AgentToolProtocol.cs` | Объявляет серверные функции модели и разбирает уточнение |
| `Agent/AgentToolExecutor.cs` | Проверяет и выполняет один шаг через MCP либо доверенную подготовку |
| `Agent/ReminderProposalHandler.cs` | Проверяет будущее время и подготавливает напоминание |
| `Agent/AgentContextBudget.cs` | Уменьшает контекст без разрыва ходов и tool_call_id |
| `Agent/AgentTimeContext.cs` | Сообщает локальное время, пояс и день недели |
| `Llm/ChatCompletionTransport.cs` | HTTP, размеры, таймаут, отмена, журнал и один ограниченный повтор |
| `Llm/LlmRequestCoordinator.cs` | Очередь и ожидание квоты отдельной модели |
| `Llm/ModelCapabilities.cs` | Изолирует отличающиеся параметры API моделей |
| `Llm/CompletionParser.cs` | Извлекает публичный текст и вызовы без reasoning |
| `Application/InteractionState.cs` | Хранит краткий контекст, номера вариантов источника и незавершённые ответы по владельцу |
| `Mcp/BotMcpClient.cs`, `McpToolCatalog.cs` | Запускают stdio-сервер, обнаруживают схемы и выполняют разрешённые вызовы |

| `Shared/Persistence/Migrations`, `Repositories` | Версии схемы и параметризованный SQL по обязанностям |

Пути в таблице относятся к `src/IntellectBot`, кроме явно обозначенных
`Shared` (`src/IntellectBot.Shared`) и `McpServer` (`src/IntellectBot.McpServer`).

## Один запрос

1. Telegram передаёт текст и доверенный ID владельца в сервис диалога.
2. Сервис читает настройки и историю из PostgreSQL.
3. Агент добавляет реальные локальные время и пояс, ограничивает контекст.
4. Модель отвечает текстом, задаёт служебное уточнение или выбирает функцию.
5. Исполнитель проверяет имя и аргументы по каталогу. Чтение выполняется через
   MCP; запись направляется в доверенный сценарий подготовки.
6. MCP-сервер повторяет проверку, получает данные источника и проверяет результат.
7. Приложение возвращает результат модели как `tool`, сохраняя исходный ID вызова.
8. Итог форматируется и сохраняется вместе с запросом. Для записи показываются
   отдельные кнопки; фактическое сохранение выполняется после подтверждения.

HTTP-вызов LLM и действие MCP — разные величины. Обычный ответ требует одного
LLM-запроса; погода обычно требует выбора инструмента и итога по его результату.
Подготовка напоминания не требует дополнительной генерации текста для кнопок.

## Уточнение города

Модель выбирает реальные ID и понятные подписи из candidates. Приложение проверяет
их и нумерует. Подпись собирается из полей MCP или его `display_name`, а не из текста модели.
Она не должна содержать координаты или дубли; модель не может подменить страну. Несуществующие ID отклоняются.

Номер, слово «один» и «а в девятом варианте?» разрешаются по исходному списку
текущего пользователя. Выбранный ID передаётся точно. Большой список не повторяется
в контексте итогового ответа; хранение выбора независимо от истории модели.

Ошибку списка можно вернуть модели для одного исправления без повторного MCP.
При квоте после получения данных сохраняется краткое продолжение на две минуты.
Повтор другого запроса и другой пользователь его не используют.

## Новый инструмент чтения

1. Создать серверный endpoint с `McpServerTool`, именем, русским Description,
   типизированными аргументами и результатом.
2. Зарегистрировать необходимые зависимости в `ServerComposition`.
3. Объявить корректный ReadOnly и outputSchema; проверить контракт через общий
   фильтр. Обычные SDK-типы дают схему автоматически.
4. Добавить автономные и отрицательные проверки, пересобрать сервер и приложение.

Клиент обнаружит метод через tools/list. Новая ветка по имени в LLM-клиенте,
валидаторе и агентном цикле не требуется. Предметные проверки принадлежат методу
сервера; закрытый входной объект не принимает лишние служебные поля.

Для нового изменяющего действия дополнительно нужны модель подготовленных данных,
постоянное состояние, доверенная подпись, UI подтверждения и адаптер исполнения.
Одного изменения ReadOnly недостаточно. Текущий адаптер подготовки предназначен
для напоминаний.

Для погодного и справочного результата сервер возвращает `public_text`.
Это обычное проверенное представление типизированных данных; оно не исполняется
как инструкция. Модель получает компактное представление tool-результата и выбирает действие.
Для погоды приложение показывает `public_text`. Для справки модель группирует
проверенные `facts`, а приложение восстанавливает их точный текст и ссылку.
При ambiguous используются реальные `candidates`: `id`, `display_name`,
`selection_arguments`. Номер пользователя восстанавливает точные аргументы,
а не запускает новый поиск по свободно сгенерированной строке.

Публичный справочный источник находится в `McpServer/Reference`, погодный —
в `McpServer/Weather`. Общая HTTP-граница и ограниченный кэш находятся в
`McpServer/Infrastructure`. Это не отдельные агентные циклы по моделям.

## Новая модель

Настройки пользователя хранят точный ID. Список интерфейса находится в
`Shared/Domain/Dialogue/LlmModels.cs`. Особенности HTTP-параметров — только в
`Llm/ModelCapabilities.cs`. Протокол функций, проверка схем и агентный цикл общие.
Новый профиль проверяется обычным ответом, чтением MCP, уточнением и подготовкой
напоминания. Автоматическая подмена модели при исчерпании квоты не выполняется.

## Данные и подтверждение

Личное расписание читается из PostgreSQL с доверенным контекстом владельца.
`data/demo-schedule.json` — автономная фикстура. Фиксированные часы
`Schedule:ReferenceTime` используются только для этой фикстуры и не меняют
время личного расписания, подписи и ОС.

Нажатие кнопки напоминания проверяет владельца, срок и параметры. MCP-вызов записи
не повторяется автоматически при сетевой ошибке. Приложение проверяет состояние
БД: потерянный ответ после commit не должен создавать вторую запись.


Повтор другого сообщения с тем же владельцем, временем и текстом напоминания
проверяется `ReminderStore`. Нормализация пробелов и регистра совпадает в
репозитории и уникальном индексе миграции `ReminderIdentitySchema`.
Подтверждённое действие сохраняет ссылку на результирующее напоминание.
`ReminderDisplay` переводит UTC в пояс напоминания до формирования `/why`.

## Компактный повторный шаг

`ToolReplyWindow` формирует контекст после MCP: текущий запрос, точное время и
целые пары assistant/tool. Дублирующиеся значения заменяются проверенным
публичным представлением, справка передаётся массивом фрагментов.
`EvidencePresentation` проверяет предложенные моделью разделы и индексы;
текст фрагментов и URL остаются данными источника. Несколько результатов одного
запроса сохраняются в итоговом ответе. Ошибка структуры не порождает новых фактов.

## Граница представления

Telegram-форматирование отделено от маршрутизации: код и перевод сохраняют
моноширность, обычный текст очищается от служебной разметки, таблицы становятся
карточками. Простая математическая запись преобразуется только вне блоков кода.
Выбранный часовой пояс читается из настроек при построении клавиатуры.

`ReminderRequestGuard` дополнительно сопоставляет аргументы с исходной просьбой
и распознанным местным временем. Проверка схемы не заменяет эту проверку смысла.
Итоговая инструкция маршрутизации хранится в `AgentToolProtocol.Instructions`;
эксперимент сохраняет её снимок в своей конфигурации.
