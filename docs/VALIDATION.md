# Проверка приложения

## Автоматические проверки

Все команды выполняются из корня репозитория.

```bash
dotnet restore --locked-mode
dotnet build -c Release --no-restore
dotnet test -c Release --no-build
dotnet format whitespace . --folder --verify-no-changes
```

Обычные тесты используют управляемые ответы вместо настоящих Telegram и LLM API. Они проверяют:

- инструкции режимов, параметры генерации и формат HTTP-запроса;
- историю, порядок сообщений, ограничения контекста и изоляцию пользователей;
- смену режима, сброс памяти и сохранение уровня креативности;
- выбор режима через кнопки настроек, навигацию и редактирование меню;
- отклонение удалённых команд `/study`, `/translate`, `/review` и `/temperature`;
- перевод с HTML-экранированием и моноширным текстом;
- длинные ответы, сохранение emoji и порядок частей;
- нетекстовые сообщения, индикатор обработки и безопасные ошибки;
- конфигурацию, маскирование секретов, состояние health и блокировки чатов;
- состав архива для облачного развёртывания.

`Fixtures/expected-ui.json` содержит эталонные тексты интерфейса: приветствие, справочные сообщения и 24 варианта настроек. Тест сравнивает их с фактическим текстом приложения.

PostgreSQL-тесты по умолчанию пропускаются. Для отдельного временного контейнера:

```bash
bash scripts/test-db.sh
```

Windows PowerShell:

```powershell
.\scripts\test-db.ps1
```

Скрипт запускает 16 интеграционных случаев и удаляет тестовый контейнер. Рабочая база не используется. Проверяются схема, ограничения, атомарность записи пары сообщений, параметры SQL, настройки, разделение пользователей и сохранение истории при открытии нового пула.

Строки `ERROR` в тестовом выводе ожидаемы в сценариях, которые специально моделируют сбои API. Результат проверок определяется итоговой сводкой тестов.

## Результаты проверки

| Проверка | Результат |
|---|---|
| Сборка Release | Без ошибок и предупреждений |
| Модульные и контрактные тесты | 136 успешных случаев |
| PostgreSQL-тесты | 16 успешных случаев по предоставленному локальному запуску |

Пропуски в обычном запуске относятся к 9 методам/группам PostgreSQL-тестов; при отдельном запуске теории разворачиваются в 16 случаев. Живой Telegram, LLM, прокси и облачное развёртывание проверяются отдельно.

## Ручная проверка

1. Запустить PostgreSQL, заполнить `.env` и запустить приложение по README.
2. Проверить `/start`, `/settings`, `/reset`. В главном меню должны быть «Сброс памяти» и «Настройки».
3. Через настройки выбрать обучение, проверку кода и перевод. При смене режима память очищается, уровень креативности сохраняется.
4. Проверить четыре значения креативности и применение нового значения к следующему запросу.
5. В переводе отправить «Что такое кортеж?» и «На немецкий: Доброе утро». Проверить перевод вопроса, заголовок направления и моноширный текст.
6. Проверить отсутствие кнопки меню при отдельной команде `/settings` и наличие возврата при открытии настроек из меню.
7. Сбросить память через меню и через `/reset`; проверить сохранение режима и креативности.
8. Запомнить контрольное слово, перезапустить приложение и проверить историю. Со второго аккаунта проверить независимые настройки и диалог.
9. Отправить фото/документ и получить объяснение о текстовых сообщениях. Проверить длинный ответ.
10. Во втором терминале выполнить `dotnet run --project src/IntellectBot -- healthcheck`.

Эксперимент с четырьмя значениями temperature находится в `docs/lab1-experiment`: 12 ответов, параметры, таблица и анализ. Сохранённые ответы и дата проведения не изменяются при обновлении документации.
